# 文書の配置と管理

2026-09-06の合意に基づく管理規則。既存文書の本文を要約・言い換えず、移動・分割・結合とリンク更新で整理する。

## 読者と掲載先

- API・Architecture・Guidesは長く参照する完成文書。Developmentを読まずに理解できるようにする。
- Architecture/Structureは責務・依存・所有・lifecycle・実行順・公開・失敗の現行契約。
- Architecture/DataFlowは値の生成・変換・保持・取得・利用・保存・復元。所有関係と値の受け渡しを同じ矢印に載せない。
- Architecture/Decisionsは実装済みの現在の境界を選んだ理由。合意済みでも未実装の設計はDevelopment/Discussionへ置く。
- APIは公開操作の正確な契約、Guidesは目的を達成する手順。Quick StartとConceptsはGuides内に置く。
- Developmentは保守担当者の内部資料。Discussionは検討対象、Historyは作業中から積み重ねる経緯、Performanceは条件・revision・結果・結論を持つ測定記録。

## 分類と名前

機能名は責務を表す安定した分類とし、Structure・DataFlow・Decisions・開発記録で同じ対象には同じ名前を使う。空の分類や転送だけの索引は作らない。

長く参照し、順番に読む説明は00_index.mdと01_以降で読む道筋を示す。番号は各ディレクトリ内の推奨読順であり、追加順・作業IDではない。APIやDataFlowの名前で検索する個別項目は連番を必須にしない。読む順番の変更時は改番と参照更新を行う。audit.mdと直接参照する管理規則は連番を付けない。

作業IDは機能名/作業名とし、Discussion・History・Performanceの項目ディレクトリと一致させる。例はPrefab/entity-activation。独立して完了できる問題だけ別IDにする。複数機能をまたぐ場合は主に変更する契約の機能へ一つだけ置く。完成文書を作業IDごとに分割しない。旧IDは過去の本文・コードの目印に保持し、移行記録で新IDに対応付ける。

記録は<分類>/<機能>/<作業名>/YYYY-MM-DD_内容.mdへ置く。日付は記録日であり、連番や優先順位ではない。同じ議論の追記だけで毎日ファイルを増やさない。測定付属ファイルは必要な場合だけ同名ディレクトリへ置く。移設した過去資料の日付の根拠は移行記録に残す。

## Discussionの状態

文書冒頭の管理情報で「合意状態：未決定／一部合意／合意済み」と「実装状態：未実装／一部実装／実装済み」を分ける。混在する場合は対象の節を明記し、不明なら未確認と記す。本文の案を配置やファイル名だけで合意済み・実装済みと扱わない。作業進捗はaudit.mdだけで管理する。

未実装の合意案もDiscussionに留め、現行Architectureの契約を上書きしない。過去の判断が更新された場合は後の記録へ理由を残す。

## Auditと完了時の処理

audit.mdには残作業・状態・完了条件・次の一手・関連記録だけを書く。候補は採否判断を残作業とし、一括実装の承認とみなさない。保留には理由と再開条件を付ける。完了・見送りの一覧や長い検証記録は載せない。

完了時は必要なStructure・DataFlow・API・Guidesと実装済みのDecisionsへ確定内容を反映し、最後のHistoryメモに結論・検証根拠・反映先を残してAuditから削除する。Discussionが全て完了・見送りならHistoryへ移す。残る案がある場合は節を分けてDiscussionへ残す。見送りでは無理に完成文書を作らない。

内部記録から完成文書へリンクし、完成文書の理解をAudit・Discussion・Historyに依存させない。nekoとKootaの台帳はそれぞれのrepository内で完結させる。

## 内容を保持する移設

既存本文は現在契約・判断理由・未実装設計・経緯・測定・手順に分類してから移す。今回の整理では本文の要約や言い換えを行わない。新しい説明は分類・状態・出典・索引・移動対応の管理情報として区別する。既存の重要な段落、表、コード例を落とさず、相対リンクとfragmentを確認する。
