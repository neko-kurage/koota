# Entityの一括生成

1万件・2数値Traitの一括生成を隔離して試作しました。最終候補の正式比較は約2.85〜2.93→1.26〜1.28ms、約55〜57%短縮でした。10条件で悪化・p95停止はありません。1ms以内には届いていません。本番のKoota・neko依存は変更していません。

## 生成する値と計時範囲

```ts
const Position = trait({ x: 1, y: 2 })
const Velocity = trait({ x: 2, y: 3 })
const entities = spawnBatch(world, 10_000, Position, Velocity)
```

同じ初期値を持つEntityを返す試作です。基準は、同じ長さの結果配列へ`world.spawn(Position, Velocity)`を順に保存します。IDの確保・所属・初期値・必要なQuery処理・結果配列への保存を生成時間に含めます。照合・破棄・Queryの遅延削除確定は計時の外です。生成中のGCを除外しません。

warmup後は同じWorldで生成・破棄を繰り返すため、IDと列の容量を再利用します。初回生成は別にcoldとして保存します。Worldの作成時間、nekoのPrefab・Scope・Activity・Component処理は含みません。1件の場面は1,000呼出しをまとめて測り、1呼出しへ換算します。

## 比較した版

基準はKoota `6c6698de82a8b37f0ad2d76dcb33de8def35606b`です。試作ごとにsource差分と上流buildのdistを凍結しました。

初期の`diagnostic-prepared`・`diagnostic-cached`は、後処理が意図せずQueryを作っていたため無効です。約5.45→4.27msなどの値は「Queryなし」の根拠に使いません。修正後は、事前にQueryを用意した場面だけ後処理でQueryを読みます。

## 通知と寿命

Queryの追加・削除購読、対象Traitの追加購読、factory、Relation、設定値、公開済みstoreなどがある場合は、既存の`createEntity(world, ...traits)`を順に呼びます。全入力の検査が終わるまでTraitを先行登録しません。途中で通知をまとめて送らず、成功済みの生成・通知を巻き戻しません。

共有する初期値は利用者処理を呼ばないSoA・tagに限り、EntityのTrait集合は各Entityが独立して持ちます。Queryがある場合はTrait単位の既存遷移を使います。世代maskの集約はQueryがない場合だけです。これは呼出し中の準備であり、新しい保持状態や通知契約は増やしていません。

通知ありの場面も速くなること、初期値が異なるPrefabへの接続、nekoを含めた生成の1ms達成は、この結果からは言えません。

## 初回生成・破棄・保持量

`isolated`の2 Trait場面では、場面内の初回生成は基準5.389〜5.422ms、候補3.778〜3.848msでした。共通関数は前の場面でも実行されているため、process開始直後のcold起動とは区別します。1.26〜1.28msは容量・IDを再利用したwarm値です。

生成中のGCを含むp95は、基準4.985〜5.709ms、候補3.696〜4.215msでした。中央値だけでなく尾も1msを超えています。破棄は基準2.860〜2.946ms、候補2.756〜2.780msでした。

空のwarm Worldから1万件を生存させた追加heapは、full GC後に両版とも約1.887MiBでした。列・IDの既存容量は空World側に残るため、この値はWorldの総保持量ではありません。Entityごとの独立したSetとWorldの所有を共有オブジェクトへ置き換えていません。

## 変更と効果の読み方

- 入口をまとめただけの`wrapper`は限定診断で約2.91→2.85msでした。反復呼出しを一つの関数で包むだけでは、1msへ近づきません。
- `final`は初期値・Trait構成・登録先の準備を共有して約46〜49%短縮しました。`grouped`は世代単位のmask反映でさらに短い候補になりましたが、通常経路の生成コードも変えたためRelationの悪化で不採用です。
- `isolated`は既存の通常関数本文を復元し、一括生成だけにmask合成を閉じました。最終比較では約55〜57%短縮し、Relationの悪化判定は残りませんでした。`check-generated.mjs`で通常生成・追加・削除・保存の5関数がbyte一致しました。
- `batch-loop`はEntityごとの初期化callback往復を避ける限定試作でしたが、約1.27msで追加の短縮が得られず、作成関数を引数へ増やす形を残していません。

異なる正式系列の中央値を引き算して、変更一つの短縮量とは断定しません。各系列はそれぞれ同時に取った基準との対応で評価します。Relationの悪化についても、helper抽出を戻した構造が今回の条件で同等になったことまでの確認であり、V8の個々の最適化判断までは特定していません。

## 契約・復元の検証

- Query通知が初期値の設定前、Trait通知が設定後という既存の順序を、途中の値とともに反復生成へ照合しました。
- 通知からの再入・Entity破棄・例外・schema変更・Query追加・World reset／終了を照合しました。成功済みの状態と通知を巻き戻しません。
- factoryの独立値と回数、設定値のgetter、Relationの対象終了、世代付きID再利用、無効化、保存履歴、公開storeのsetter、0件・不正件数を確認しました。
- Queryを後から作る構成、64 Traitで世代をまたぐmask、1件のTrait除去が他Entityへ伝わらないことを照合しました。
- 独立した復元先へ固定lockfileからoffline installし、型、collections 24件・core 178件・React 37件、配布用215件のテストとpackを通過しました。今回の追加は16ケースです。
- 凍結distと復元buildの11 fileはすべてSHA-256が一致しました。13版のsource差分の復元も確認しています。sourceと契約テストのSHAを`versions.json`で検査します。

最終候補の本番src差分は+123行です。新しい保持field・永続cacheはありません。Lizard 1.24.0では`spawnBatch`がNLOC 24／CCN 9、`prepareBatchTraits`が46／22、`markTraitInMasks`が14／3でした。準備関数は、通知・factory・公開storeなどの早期分岐と、登録・mask準備・適用の段階を一か所で追える形を維持しました。基準値を満たすためのhelper分割はしていません。

coreのlintはエラー0、既存の`RelationTarget`未使用import警告が1件です。今回の変更ファイルに新しい警告はありません。二つの変更ファイルを専門担当が点検し、型・命名・段階を整理した版を正式比較しました。

最終候補は本番へ入れていません。コミット・push・vendor変更はありません。

## 残る判断

1msを達成するには、最終候補から約0.27ms、約21%の追加短縮が必要です。空Entityでも約0.65msかかります。ID確保・独立した所属集合・Worldの索引・結果配列を含む費用であり、この診断だけで内訳を一つへ帰属できません。

次はEntity管理の保持形式を測り分ける余地があります。`entityTraits`のpacked IDをkeyにしたMapと、EntityごとのSetをどう持つかは通常の追加・除去・破棄にも関わります。一括生成だけの専用状態を足す前に、全操作で使う表現として検討する必要があります。
