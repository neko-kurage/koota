# 削除通知への再入で連鎖が欠ける問題の修正

作業ID：Entity/reentrant-destroy。2026-09-06、ユーザー依頼によりfeature/reentrant-destroyで実施。基準ac000e2。直前のEntity契約に関する文書整理は保持し、今回のruntime修正はEntity削除処理へ限定した。

## 再現と原因

現在のforkでも、親のMark除去通知で別Entityをdestroyすると、autoDestroy: source/targetの連鎖先が生存した。同じ個体を通知内でdestroyすると無限再帰した。修正前の回帰テストは4ケースとも失敗。

共有queueとSetをdestroyの入口で初期化していたため、再入が外側の待ち一覧を消していた。共有配列を保持したまま各呼出しが開始時の長さより上だけを処理する。処理開始済みの集合は再入全体で共有し、最後の呼出し終了でclearする。finallyで呼出し範囲を片付けるが、ゲーム状態は戻さない。

## 結果

source/target両方向、同じ個体・削除待ちの子への再入、世代再利用、別Worldの例外を捕捉して外側の連鎖を続ける4ケースが成功。verify-forkは型検査、collections 23・core 150・React 37のsourceテスト、生成配布187テスト、build、packまで成功した。

[通常経路の測定](../../../Performance/Entity/reentrant-destroy/2026-09-06-measurements.md)で大きな悪化は見られず採用。[現行の削除契約](../../../../Architecture/Structure/Entity/02-destruction.md)へ反映してAuditの修正項目を削除した。公開・merge・commitはこの作業では実施していない。nekoの同梱tgzはac000e2のまま。更新した配布物の導入はKoota/distributionと利用側のfork-integrationで追跡する。

測定準備で見つけた「削除後に初めて空Queryを作ると死んだEntityが返る」問題は、修正前後の別processで再現する別件。Query/initial-populationへ記録し、この修正には混ぜない。
