# Audit：作業状態を残す

Auditは、合意した作業、改善候補、残っている確認を、人と次の担当者が確認できる作業台帳です。複数回にまたがる作業や候補を比較する作業で使います。小さな修正のたびに新しい台帳を作る必要はありません。

## 入口と保存先

台帳は[fork Audit](../../../audit.md)。現在地、未完了の全項目、検討順、完了・見送りをここ一か所で更新する。履歴の進行状況はHistoryへ移し、現在欄へ未コミット・未着手の古い説明を残さない。実測値はperformance、検討時点の資料はhistoryに置く。neko側のAPI要件はnekoの台帳で管理し、同じ候補の状態を転記しない。

## 状態の付け方

| 状態     | 意味                                           |
| -------- | ---------------------------------------------- |
| 候補     | 問題と改善案を記録した段階。採用・実装は未決定 |
| 未着手   | 実施することが決まっているが、作業前           |
| 作業中   | 調査・設計・実装を進めている                   |
| 検証待ち | 変更はあるが、必要な確認が残っている           |
| 完了     | 完了条件を確認し、その根拠を記録した           |
| 保留     | 進めない理由と、再開条件を記録した             |
| 見送り   | 採用しない理由を記録した                       |

各項目は安定したID、何をどう変えるか、状態、完了条件、根拠を持ちます。未確認は未確認と書きます。「コードを書いた」と「動作・効果を確認した」を分け、測定していない性能改善を完了扱いにしません。候補の列挙は一括実装への合意を意味しません。

## 更新するタイミング

- 作業開始・再開時：該当する台帳、実際の差分、記録されたrevisionを確認し、今回扱う項目と次の作業を合わせる。
- 方針変更・中断時：変わった状態、判断理由、未解決事項、次に行う具体的な作業を更新する。
- 検証後・引き渡し前：実行した確認と結果を追記し、完了条件を満たす項目だけ完了にする。最終回答から台帳へリンクする。

最新状態が一覧で分かるようにし、履歴は重要な判断だけを短く残します。コミットの有無は作業状態と分けて記録し、未コミットならそう明記します。コミット作成はユーザーの依頼または合意した手順に従います。

## 台帳に残す最小限の内容

テーマの目的、更新日、対象revision、現在の状況と次の作業を先頭に置きます。その後に項目一覧、必要な実装上の注意、検証根拠と判断履歴を記録します。専用ツール、定期通知、全項目共通の大規模な検証は必要ありません。確認内容は変更に応じて選びます。
